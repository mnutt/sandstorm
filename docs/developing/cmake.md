# Building Sandstorm with CMake

Sandstorm is built with CMake and Ninja. Use the checked-in presets described here for development,
release, and continuous-integration builds.

The checked-in presets use the Chromium Clang toolchain downloaded into `deps/llvm-build`, matching
the compiler used for Sandstorm releases. Bootstrap it before configuring a development or release
preset:

```sh
git submodule update --init deps/clang
deps/clang/scripts/update.py --output-dir deps/llvm-build
test -e deps/llvm-build/bin/clang++ || ln -s clang deps/llvm-build/bin/clang++
```

Configure and build a development tree:

```sh
cmake --preset dev
cmake --build --preset dev
ctest --preset dev
```

Native binaries are written to `build/dev/bin`, libraries and `capnp.node` to `build/dev/lib`, and
generated sources to `build/dev/generated`. Nothing generated by the native build is written
to `src` or the repository-level `bin` and `tmp` directories.

To create the layout consumed by the frontend and bundle build:

```sh
cmake --build --preset dev --target stage-native
```

This writes binaries, the Node addon, and schemas to `build/dev/stage` rather than the
repository-level `bin`, `tmp`, and `node_modules` directories.

The frontend environment and Meteor bundle can be built independently:

```sh
cmake --build --preset dev --target shell-env
cmake --build --preset dev --target shell-build
```

`shell-env` installs the pinned icon and shell npm dependencies, generates the icon assets and
changelog template, and stages the native runtime. `shell-build` writes the Meteor application to
`build/dev/shell-build`; `shell-build-debug` produces a debug Meteor build. Generated assets remain
in `shell/` for now because Meteor consumes that source layout.

Ninja performs incremental rebuilds, so re-run `cmake --build --preset dev` after making changes.
The former persistent watch mode does not have a direct CMake target.

Run the frontend checks with:

```sh
cmake --build --preset dev --target lint
cmake --build --preset dev --target typecheck
```

Configure with `-DSANDSTORM_BUILD_FRONTEND=OFF` when only native targets are needed and frontend
tools such as `markdown` and Meteor are not installed.

Ninja's standard `clean` target removes outputs owned by one build preset. Frontend dependency
directories are shared across presets and can be removed separately:

```sh
cmake --build --preset dev --target clean
cmake --build --preset dev --target clean-frontend
```

Do not run `clean-frontend` concurrently with another frontend build. Its stamps are removed along
with the npm and Meteor dependency directories, so the next frontend target reinstalls them.

Update the pinned dependency submodules from the branches recorded in `.gitmodules` with
`git submodule update --init --remote --rebase`. This is intended for deliberate dependency update
work, not as a prerequisite for normal builds.

Continuous integration uses the `ci` preset, which selects the system Clang toolchain and ccache:

```sh
cmake --preset ci
cmake --build --preset ci
ctest --preset ci
```

On a fresh worker, install the Meteor launcher and run a pinned-release command before configuring.
The launcher does not guarantee that the toolchain named by `shell/.meteor/release` is present; the
first such command downloads it and refreshes Meteor's catalog. CI performs that bootstrap in its
Meteor installation step so CMake's dev-bundle lookup remains a local filesystem operation. The
launcher, pinned `meteor-tool` package, and catalog metadata are cached by the release-file hash;
unchanged releases therefore skip both the launcher installation and toolchain download.

Build the signed test application package with:

```sh
cmake --build --preset dev --target test-app-spk
```

The result is `build/dev/packages/test-app.spk`. The `app-index-spk` target produces the app index
package and requires its signing key in `~/.sandstorm-keyring`; set
`SANDSTORM_APP_INDEX_KEYRING` at configure time to use another keyring.

Run the built-in applications against a local Sandstorm server in SPK development mode with:

```sh
cmake --build --preset dev --target test-app-dev
cmake --build --preset dev --target app-index-dev
cmake --build --preset dev --target meteor-testapp-dev
```

These are foreground processes. Stop a development session with Ctrl-C before starting another.

`meteor-testapp-spk` builds the Meteor application fixture used by the browser system tests. Run
the complete system-test workflow against CMake-built artifacts with:

```sh
cmake --build --preset dev --target system-test
```

The server bundle and release archives are also available as explicit targets:

```sh
cmake --build --preset release --target bundle
cmake --build --preset release --target package
cmake --build --preset release --target package-fast
```

Bundle assembly uses `build/release/stage` and `build/release/shell-build`, writes the expanded
bundle to `build/release/bundle`, and retains downloaded database payloads in the repository's
existing `hack/` cache. Release archives are written to `build/release/packages`. The regular
archive uses maximum compression; `package-fast` uses parallel low compression for development.

Install a new development server from the fast archive, or update an existing local installation:

```sh
cmake --build --preset release --target install-local
cmake --build --preset release --target update-local
```

`install-local` runs `install.sh` interactively. `update-local` runs `sudo sandstorm update` and
therefore applies only to an installation configured to run at startup.

The root `Makefile` is a temporary compatibility layer for common historical commands. It invokes
the CMake presets and does not implement a separate build. New scripts and documentation should
call CMake directly.

`release.sh` uses the `release` preset and runs the native tests before creating the maximally
compressed archive. It still expects the release Clang toolchain in `deps/llvm-build`; bootstrap
that compiler with the Chromium downloader above when it is not already present.

The legacy VM-based installer suite is available through `installer-test`:

```sh
cmake --build --preset dev --target installer-test
```

Its preparation script installs or downloads Vagrant tooling and old VM images as needed. Configure
`SANDSTORM_STODGY_TESTER` if `stodgy-tester` is not installed at `~/.local/bin/stodgy-tester`.
